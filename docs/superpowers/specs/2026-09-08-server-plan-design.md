# Change Pilot Agent Server — Design Proposal

> **Status:** Design proposal. Not implemented. The shipped Change Pilot artifact is the skill at `.claude/skills/change-pilot/`; this document describes a future server that would expose the skill's transformation capability over HTTP.
>
> **Source of truth:** This server design explicitly states that the Server does **not** implement Change Pilot rules — the skill is the single source of truth. Any server built from this spec must delegate transformation to the skill, not re-implement its rules.

这里有一个原则：

Server 不实现 Change Pilot 规则，Skill 才是唯一业务规则来源。

你的现有 Skill 已经定义了“保留业务事实、隐藏内部细节、技术抽象、不夸大、变化类型识别、多变更拆分”等核心行为，因此 Server 只是把它服务化。

## 2. 为什么采用这个架构

你最初提出的是：

Claude Code 常驻后台
        ↓
REST API
        ↓
发送消息
        ↓
Claude 回复

这个方向没问题。

但如果直接实现：

FastAPI
   ↓
常驻 claude stdin
   ↓
stdout

后面很容易遇到：

Session 管理
Claude 进程异常退出
并发
超时
流式输出
上下文污染
进程僵死
服务重启
Session 恢复

因此 V1 采用：

常驻的是 Change Pilot Server

Claude Code：
按 Task 启动 / 执行 / 恢复

而不是强行让一个 Claude CLI 永远挂在那里。

Claude Code 的程序化 CLI 能力适合这个方案；同时 Anthropic 当前也已经提供了更完整的 Agent/SDK 体系，因此我们把 Claude 调用封装在 AgentRunner 后面，未来切换实现不会影响 REST API。

## 3. V1 的核心原则

整个项目严格遵循：

### 原则 1：Skill 是唯一业务真相
rules/
prompts/
schemas/
examples/
tests/
SKILL.md

决定 Change Pilot 的行为。

### 原则 2：Server 不理解业务

Server 不应该出现：

if "commit" in text:
    ...

也不应该：

prompt = "隐藏代码路径..."

Server 只知道：

request
 ↓
agent
 ↓
response
原则 3：REST 是业务接口，不是 Claude CLI 接口

外部调用：

POST /v1/change-pilot

而不是：

POST /v1/claude

因为用户真正调用的是：

Change Pilot 能力。

不是：

Claude Code。

### 原则 4：默认无状态，Session 是高级能力

Change Pilot 本质：

输入变更点
      ↓
输出客户描述

所以默认：

request A
 ↓
response A

和：

request B
 ↓
response B

互不影响。

## 16. V1 Claude 调用策略

第一版：

POST /v1/change-pilot
        ↓
AgentManager
        ↓
ClaudeRunner
        ↓
claude -p

核心思想：

Server 常驻

Claude Task 生命周期：
启动 → 执行 → 返回 → 退出

对于 Change Pilot 这种：

一次输入
→ 一次分析
→ 一次输出

实际上非常合适。

## 17. Session 场景

如果：

POST /v1/chat

第一次：

claude -p

拿到：

claude_session_id

保存：

cp_sess_001
       ↓
claude_session_id

第二次：

claude --resume xxx -p

这样可以恢复上下文。

## 18. 为什么不要所有请求都 Session

因为 Change Pilot 的业务逻辑本来就是：

R&D Change
      ↓
Customer Change

不需要记忆之前请求。

如果所有请求共享：

一个 Claude Session

可能出现：

请求 A：
扫码问题

请求 B：
网络问题

请求 C：
安全问题

Claude：
结合前面的扫码……

这就污染上下文了。

因此：

/v1/change-pilot

默认：

stateless
/v1/chat

支持：

stateful

这个设计非常重要。

## 22. CLAUDE.md

Server 的 Agent Runtime 可以提供：

/opt/change-pilot/runtime/CLAUDE.md

内容只负责：

你是 Change Pilot Agent。

当用户要求处理研发变更点时：
1. 使用 change-pilot skill
2. 遵守 Skill 中所有规则
3. 默认只输出 customer-facing result
4. 不修改代码
5. 不执行危险命令

SKILL.md
CLAUDE.md
core-rules.md
